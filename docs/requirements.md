# Бизнес-требования

## 1. Контекст

ЦИПСО моделирует централизованный реестр электронных повесток **военного учёта**. Система хранит сведения о призывниках, военкоматах, повестках, сроках явки, статусах оповещения, обращениях, документах и аудите.

Проект учебный: реальных государственных интеграций и реальных персональных данных нет.

## 2. Роли

| Должность | Системная роль | Права |
|---|---|---|
| Секретарь | Operator | Чтение и изменение данных |
| Комиссар | Manager | Чтение/изменение, история и контроль |
| Призывник | Observer | Чтение и предусмотренная подача документов |
| Инженер автоматизации военно-учётного стола | AutomationEngineer | Создание учётных записей и эксплуатационные функции |

## 3. Аутентификация

- локальные логин и пароль не используются;
- вход предусмотрен через MAX либо Госуслуги с «Госключом»;
- после успешной внешней аутентификации система выдаёт JWT;
- самостоятельная регистрация отсутствует;
- текущая учебная реализация использует две mock-заглушки внешнего входа;
- учётные записи создаёт AutomationEngineer.

## 4. Основные бизнес-правила

1. Повестка относится к одному призывнику и одному военкомату.
2. Номер повестки уникален.
3. Срок явки не может быть раньше даты формирования повестки.
4. Изменение статуса фиксируется в `SummonsStatusHistory` и `AuditEvent`.
5. Отправка mock-уведомления создаёт `Notification` и `DeliveryAttempt`.
6. Обращение относится к конкретной повестке.
7. Документы в MVP хранятся как метаданные.
8. Все рабочие endpoint'ы требуют JWT; исключения — вход и health.
9. Призывник не может создавать или менять повестки.
10. Реальные персональные данные запрещены в учебном контуре.

## 5. Нефункциональные требования

- запуск через Docker Compose;
- PostgreSQL;
- REST/JSON;
- Swagger/OpenAPI;
- frontend и backend разделены;
- запуск на Linux/Windows через Docker Desktop;
- CI проверяет backend tests и frontend build.
