# Бизнес-требования

## 1. Контекст

Организации, которым требуется централизованно вести списки оповещений, нуждаются в едином реестре адресатов, документов, статусов и истории коммуникаций. Учебная система моделирует этот процесс без подключения к реальным государственным сервисам.

## 2. Цель

Создать веб-приложение, которое позволяет оператору:

- регистрировать адресатов и подразделения;
- создавать электронные повестки;
- отслеживать жизненный цикл повестки;
- фиксировать уведомления и попытки доставки;
- хранить обращения и документы;
- видеть историю изменений и аудит.

## 3. Роли пользователей

- **Оператор** — создает и изменяет записи.
- **Руководитель** — просматривает реестр и контролирует статусы.
- **Наблюдатель** — только чтение.

В первом учебном инкременте авторизация не является блокирующей частью MVP; роли моделируются на уровне предметной области и будут подключены к Identity в roadmap.

## 4. Основные бизнес-правила

1. Повестка всегда относится к одному адресату и одному подразделению.
2. Номер повестки уникален.
3. Срок явки не может быть раньше даты выпуска.
4. История статусов не удаляется.
5. Отправка уведомления создает запись уведомления и хотя бы одну попытку доставки.
6. Обращение относится к конкретной повестке.
7. Реальные персональные данные в учебной среде не используются.
8. Каждое изменение статуса должно быть отражено в аудите.

## 5. Нефункциональные требования

- запуск на Linux через Docker Compose;
- потребление памяти должно оставаться разумным для ноутбука с 8 ГБ ОЗУ;
- REST API документируется через OpenAPI/Swagger;
- PostgreSQL — основная БД;
- frontend и backend разворачиваются независимо;
- архитектура допускает замену mock-уведомлений на внешний провайдер;
- основные ошибки API возвращаются в формате Problem Details.

## 6. Ограничения MVP

- нет интеграции с реальными системами идентификации;
- нет реальной отправки SMS/e-mail;
- вложения хранятся только как метаданные;
- для первого запуска применяется `EnsureCreated`, затем — EF migrations.
